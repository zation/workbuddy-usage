# 用量统计 Spec

## 背景与目标

WorkBuddy 把每次对话的 token 用量写在会话 jsonl 中，把积分写在本地 sqlite 中，两者都没有跨会话的汇总视图。本交付提供一个本地 Web 面板，按日期、分组、对话、模型四个维度呈现 token 与积分消耗。

目标：任取一个数字，都能从原始数据按本文档的口径复算出来。口径之外的一切（金额估算、余额、有效期）不在范围内。

## 范围与非目标

**范围**

- 读取 `~/.workbuddy/projects/**` 下的会话 jsonl 与 `~/.workbuddy/workbuddy.db`，只读。
- 指标：输入 token、输出 token、缓存命中 token、合计 token、积分、请求数、会话数。
- 维度：日期、分组、对话（会话）、模型；支持任意组合筛选与逐层下钻。
- 界面：**Token 与积分分成两个模块**，各自独立呈现；两模块共用时间、分组、对话、模型四个筛选条件。

**非目标**

- 不导出（CSV / 图片 / 分享链接）。
- 不关注积分有效期、余额与赠送额度，只统计消耗量。
- 不做上下文容量提示（不使用 `used` / `size`）。
- 不做多用户、鉴权、云端部署、实时推送。
- 不按官方计价规则反推金额。
- **不追溯补齐本地已不可读的数据**：WorkBuddy 清理会话后消失的积分与日志，以及本地本就没有记账的子代理积分，都不补齐、不估算。
- **不提供额外的排除开关**（如"排除已删除会话"）：筛选条件只有时间、分组、对话、模型四项。

## 用户或系统行为

1. **模块结构**：面板分 Token 与积分两个模块，不混排指标。两模块共用同一组四个筛选器：时间、分组、对话、模型；默认时间范围为**今天**。
2. **Token 模块**：合计 / 输入 / 输出 / 缓存命中 token、请求数、会话数的指标卡，按天趋势、四个维度的分布与占比、请求级明细表。
3. **积分模块**：积分合计、覆盖率（有积分记录的请求数 / 总请求数）、请求数，按天趋势、四个维度的分布与占比、请求级明细表。
4. **时间筛选**：预设（今天 / 近 7 天 / 近 30 天 / 本月 / 全部）或自定义起止日期，所有视图联动。**时间粒度固定按天**，不提供周 / 月分桶。
5. **图表**：堆叠只按**模型**分不同颜色，不按分组或对话着色。
6. **下钻**：点击某个分组或模型，将其加入筛选条件并回到当前模块；点击某个对话，进入该会话的请求级明细。
7. **明细与排序**：请求级表格，列为时间、分组、会话标题、模型、输入 / 输出 / 缓存 / 合计 token、积分；支持按任一指标排序。各模块默认按各自主指标降序（Token 模块按合计 token，积分模块按积分）。
8. **刷新**：触发一次刷新（文件增量 + 积分挂接），完成后提示扫描文件数、新增或更新请求数、补挂积分条数、耗时。

## 业务规则

**R1 数据范围**
扫描 `projects/*/*.jsonl`（主会话）与 `projects/*/*/subagents/*.jsonl`（子代理会话）。忽略所有 `.ndjson`（如 `*.file-rollback.ndjson`）与 `subagents` 之外的非 `.jsonl` 文件。

**R2 请求识别**
一条记录构成"用量步骤"的条件是：同时具备 `providerData.conversationRequestId` 与非空的 `message.usage`。缺少任一条件即忽略。

**R3 用量按请求去重（核心口径）**
同一 `conversationRequestId` 可对应多条步骤记录（当前约 91% 的请求含多步骤），其 `usage` 数值通常单调递增，表示"截至该步的累计值"。该请求的用量取**步骤中 `total_tokens` 最大的一条**，同时取该条的 `input_tokens`、`output_tokens`、`cache_read_input_tokens`，保证四项同源。
不得对各步骤求和，也不得按时间戳取最后一条代替最大值（实测存在反例）。实测逐条求和会把总量放大 22 倍以上。

**R4 日期归属**
取该请求所有步骤中最早的 `timestamp`，按其**本地时区**折算为日期。跨零点的请求归入发起日。

**R5 分组归属**
- 分组维度取值来自 `sessions.cwd`，与 WorkBuddy 桌面端新版的"分组"命名一致；不使用 `sessions.group_id` / `group_title`。
- 主会话：由文件名得到会话 ID，取 `sessions.cwd`。
- 子代理：取文件路径中 `subagents` 上一级目录名（父会话 ID），取该会话的 `sessions.cwd`。
- 仍取不到时归入 `未知分组`。不以 jsonl 目录名反解路径（该编码有损）。

**R6 对话归属**
- 主会话的请求归入该会话。
- 子代理的请求归入其**父会话**，不单独作为"对话"出现。
- 会话展示名依次取 `custom_title`、`title`、会话 ID 前 8 位，在派生维表算好后由服务层 JOIN 取得；维表行缺失时回退会话 ID 前 8 位。

**R7 模型归属**
优先取请求级 `providerData.model`；缺失时回退该会话的 `sessions.model`；仍缺失归入 `未知模型`，但保留其用量，不丢弃。模型展示名存于模型维表，同一标识出现多种写法时按固定优先级规范化（见 [data-model.md](../data-model.md)）。

**R8 积分归属**
取 `session_usage.credit_json[conversationRequestId]`，一个请求一个值。**无记录时记 0，不估算、不按 token 比例分摊。** 覆盖率按"有积分记录的请求数 / 全部请求数"计算，分母包含子代理请求；快照见 [integration.md](../integration.md)。面板须同时展示覆盖率，避免把"记 0"误解为"免费"；"积分值为 0"与"没有积分记录"必须分别计数。
积分挂接是独立刷新通道：每次刷新无条件重读 `session_usage`，只更新当前映射中存在的请求；映射外的行不触碰、不主动清零。只统计本地此刻能读到的记录，已不可读的不追溯补齐。

**R9 已删除会话**
不按 `sessions.deleted_at` 过滤，也不提供排除开关。已删除会话只要本地仍能读到 jsonl 就计入统计；这类会话通常只剩 jsonl 中的 token，`session_usage` 行已被清理，积分按无记录处理。

**R10 空会话**
没有 jsonl 文件的会话不产生任何请求记录，也不出现在对话维度中。

**R11 幂等**
同一 `conversationRequestId` 若在多个文件或多个目录中出现，按 R3 取全局最大值合并，只计一次。

**R12 筛选条件**
筛选条件只有时间、分组、对话、模型四项，之间为逻辑与；端点以 `from` / `to`（含首尾，按本地日期）表示时间。时间粒度固定按天。

**R13 一致性**
同一筛选条件下，任一维度拆分后的各项指标之和必须等于总览合计（浮点累加误差除外）。

**已确认决策**

- 子代理请求**计入**总量：token 计入并归入父会话，本地无积分记录时记 0、通过覆盖率体现，界面标注"子代理无本地积分记录"，不补齐、不追溯。
- 只统计本地此刻能读到的数据；会话被清理或本地无记账造成的积分缺失不补齐。
- 时间戳实测零缺失，不设"未知日期"分支。
- Token 与积分分两个模块，默认今天、只按天、图表只按模型堆叠着色。

## 边界情况

| 情况 | 处理 |
| --- | --- |
| jsonl 最后一行正在写入，JSON 不完整 | 跳过该行，下次刷新补齐；不记为损坏 |
| 文件在两次扫描之间被 WorkBuddy 删除 | 从索引中移除对应请求，保持与原始数据一致 |
| 文件内容被回滚、截断或重写，部分请求消失 | 按 `source_file` 原子替换该文件的请求行，不残留已消失的请求 |
| `credit_json` 为 NULL、`{}` 或非法 JSON | 视为无积分记录，记 0，不中断解析 |
| `usage` 中 `total_tokens` 缺失或为 0 | 用 `input + output` 兜底；仍为 0 则保留请求但标记异常 |
| 累计值非单调（个别步骤数值回退） | 仍取 `total_tokens` 最大值那条，不按时间末条、不做差值推算 |
| 同一 `model` 标识出现多种展示名 | 按固定优先级规范化后写入模型维表，结果与文件遍历顺序无关 |
| 自定义模型与原生模型标识相同 | 模型维表按 `(model, source)` 联合唯一区分，不合并；`source` 当前统一为 `workbuddy`，待日志提供可区分字段后填充 |
| 子代理请求无本地积分记录（已确认计入） | 计入 token 并归入父会话，积分记 0、覆盖率中体现，不补齐 |
| 会话 `cwd` 为空但有 jsonl | 归入 `未知分组`，不丢弃请求 |
| 同一会话跨多个 jsonl 文件续写 | 按会话 ID 合并，请求按 R3 去重 |
| 时间戳缺失或非数字 | 跳过该条步骤并计入解析告警，不生成"未知日期" |

## 验收标准

- **AC1 可复算**：任取 3 个请求（含多步骤、含子代理、含无积分记录各一），面板显示的四项 token 与积分，等于按其原始记录手算的值。
- **AC2 去重生效**：全局合计 token 显著小于步骤直接累加值（约 1:22，量级见快照），且等于按请求取最大值后的合计。
- **AC3 维度一致**：在"全部时间 + 无筛选"下，分组、模型、对话三种维度各自的指标求和分别等于总览合计。
- **AC4 增量刷新**：数据无变化时刷新耗时 < 1 秒，且不重新解析任何文件（积分挂接仍执行）。
- **AC5 全量重建**：删除派生索引后首次全量解析 < 30 秒（数据规模见 [integration.md](../integration.md) 实测快照）。
- **AC6 子代理覆盖**：快照中的 8 个子代理请求全部被计入，并归属到各自父会话的分组与对话；积分显示为无记录。
- **AC7 空值兜底**：人为移除某会话的 `sessions` 行并重新解析后，面板仍能展示其用量、分组回退为 `未知分组`，不报错、不丢数据；未重新解析前，分组归属保持原值（见数据模型 C7）。
- **AC8 覆盖率可见**：总览显示"有积分记录的请求数 / 总请求数"，与按 R8 的统计一致。
- **AC9 积分独立刷新**：在 jsonl 全部未变化、仅 `credit_json` 新增一条记录的情况下触发刷新，该请求的积分被补上，其余请求已读到的积分值不变。
- **AC10 文件原子替换**：人为从某 jsonl 中移除一个请求后触发刷新，该请求从所有视图消失，同文件其它请求的数值不变。
- **AC11 界面结构**：首屏默认今天；Token 与积分分两个模块，各自只有时间、分组、对话、模型四个筛选条件；趋势粒度只有天；图表堆叠只按模型着色。

**参考基线**：以 [integration.md](../integration.md) 的实测快照为准（WorkBuddy 运行中数据持续变化，仅作量级校验，不作断言）。不在本文件重复维护具体数值。
