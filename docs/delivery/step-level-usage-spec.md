# 逐步用量口径修正与费用比率重算 Spec

## 背景与目标

面板把「请求内 `total_tokens` 最大的那一步」的四个 token 字段当作该请求的总量（C2 / AD-2），依据是 `docs/integration.md` 的「累计用量特性」：同一 `conversationRequestId` 下各步数值单调递增，被判定为「截至该步的累计消耗」，因此逐条相加会重复计算约 40 倍。

只读复核原始日志后确认该前提不成立。每条带 `usage` 的记录是**一次独立的模型 API 调用**：

- `providerData.usage.requests` 每条恒为 `1`；`message.usage` 与 `providerData.rawUsage` 的 `prompt_tokens` / `completion_tokens` 逐字段相等。
- `rawUsage.prompt_cache_hit_tokens` 约等于上一步的 `prompt_tokens`（前缀缓存命中），`prompt_cache_miss_tokens` 是本步新增部分；`output_tokens` 在同一请求内非单调（如 56 → 290 → 63 → 391）。
- `input_tokens` / `cache_read_input_tokens` 单调递增只是对话上下文随步骤增长；上下文压缩时会出现回落（实测 270,284 → 35,420），此前被当成「数值回退」。

也就是说，Agent 每执行一步都会把完整上下文重新发给模型，这些 token 都真实计费。C2 取最大快照等于只计了一次调用，而 WorkBuddy 的积分是逐步累加的（`credit_json` = 该请求所有消息步之和），分子分母因此错开一个「请求内调用次数」维度。

后果有两层：

1. **全面板 token 统计系统性低估**，且不是统一缩放——不同模型低估倍数从 1.0 到 30.7 不等，按模型堆叠的形状与相对占比同样是错的。
2. **DeepSeek 费用比率的分母少算约 20 倍**，比率被推到 1 以上，与「WorkBuddy 更便宜」的事实相反。

目标：把「每次模型调用」确立为用量事实层，请求级 token 与官方等效费用都由逐步求和派生；把比率修正到正确量级；同时让价目表变更、节假日表更新、新增模型或新口径只影响派生重算，不必重扫日志或改解析规则。

## 业务规则

**R1 逐步用量事实。** 一次模型 API 调用是一条独立用量事实：时间戳、模型标识、是否子代理直接取该条原始记录；四项 token 取 `message.usage` 的 `input_tokens` / `output_tokens` / `cache_read_input_tokens` / `total_tokens`，与 `providerData.rawUsage` 的实测对应关系记入 `integration.md`。四项之间满足 `total = input + output`、`cache_read ≤ input`；官方等效费用按 `cache_read` 为命中输入、`input − cache_read` 为未命中输入、`output` 为输出分档计价，与既有 `officialCost` 一致。请求级四项 token = 该请求全部步骤对应字段之和，Step 事实逐条落这四项，`step_count` 等于该请求的 Step 条数。不得取最大值、不得按时间取末条、不得各字段分别取极值。上下文压缩导致的数值回落不构成异常，回落前后的调用都要计入。

**R2 统计粒度与恒等。** 本次是 Step 与 Request 两种粒度并存，不是二选一：**Step 是 token 与档位的事实粒度**——四项 token 由该请求全部步骤求和，闲时档位按每步时间戳判定，官方等效费用按逐步分档计价；**Request 是模型、积分与计数粒度**——模型归属、积分、请求数、会话数、请求明细行，以及日期 / 分组 / 对话归属，全部按请求。`credit_json` 是请求级、不可分割，逐请求计数与分会话统计本就是产品语义；`date_key` 继续由该请求最早步骤的 UTC+8 业务时间派生（AD-6 / C5）。`total = input + output`、`cache_read ≤ input` 在逐步求和后仍成立，按请求聚合后校验；单步请求的结果与旧口径一致。

**模型归属取请求级**：一个请求视为只属于一个模型，取该请求**第一步**的模型标识，作为整个请求（含全部步骤的 token、积分、请求明细展示与按模型筛选）的模型。实测 494 个请求全部为单模型；若出现多模型，记录解析告警但不改变归属，不按 token 占比或出现次数选主模型，不做按步分摊，也不在明细里展示多个模型。Step 事实仍保留各自模型标识，仅用于对账与告警，不参与聚合分组与筛选。因此服务层按 `m.model` 分组、筛选、堆叠与分段的语义保持不变。

**R3 闲时档位按步判定。** 每一步按自己的时间戳，用固定 UTC+8 折算后按 DeepSeek 官方规则判高峰 / 空闲：北京时间周一至周五、非中国法定节假日的 09:00–12:00 与 14:00–18:00 为高峰，其余为空闲；周末与法定节假日全天空闲。不再与请求级 `started_at` 绑定。跨档的长请求按各自档位分别计价。

**R4 官方等效费用（分母）。** 当天、匹配四个筛选、且**所属请求模型**在 `deepseek-v4.1-flash` 白名单内的步骤，按 R3 分档后分别累加命中输入、未命中输入、输出，套 `docs/deepseek-pricing.md` 的价目表求和，两档再相加。价目表是唯一真源，官方调价只改常量。本地缓存命中视作官方上下文缓存命中的假设继续有效。

**R5 摊销费用（分子）。** `Σ(credit_json[request_id]) × 单价(该请求 date_key 所属自然月)`，其中 `单价 = 56 / (4000 + 100 × 该月自然日数)`；跨月区间各天用各自月份单价，不做区间平均；无积分记录按 0。名称与文档统一为「摊销费用」，不得称「实付」：订阅制下实付是每月固定 56 元，与用量无关，本地也没有余额与有效期数据可供定义「这批用量实际花了多少钱」。

**R6 积分真源。** 分子只能用请求级 `credit_json`，不得改用逐步 `rawUsage.credit` 求和或 `original_credit`（实测 37 个请求不一致、净差 24.86；225 个请求在本地账本无键但步骤仍带逐步 credit）。`has_credit` 仍只用于对账，不参与展示；积分为 0 与无积分记录仍按 C6 区分但不进入比率展示。

**R7 比率。** `ratio = 摊销费用 ÷ 官方等效费用`，无量纲，大于 1 表示 WorkBuddy 更贵。分母为 0 时该日 `ratio` 为 `null`；分子为 0 时如实为 0。分子分母必须共用同一筛选范围；只返回有 DS 请求的日期，范围内无 DS 请求时 `ratios` 为空数组。

**R8 派生规则一致性。** 节假日表更新、官方调价、口径扩展时，历史数据必须按新规则一致地重算，不得留下按旧规则判定的历史结果；若判档结果仍落库，则沿用「更新节假日表必须递增 `SCHEMA_VERSION` 删库重建」的既有机制，若改为查询时判定则不得再保留请求级 `is_deepseek_offpeak` 参与比率。判定发生在哪一层、是否触发索引重建属于 Plan 的技术方案，但两种方案都必须给出历史数据一致性的验证方式。

**R9 结构兼容。** 四个数据读取端点的字段名、顺序、粒度与 `rows` / `ratios` 形状不变，只有数值变化；`/api/refresh` 与 `/api/health` 的响应不变。按模型分组与筛选的语义不变。面板层继续只渲染 API 结果，不自行求和或换算。`formatTokens` 的 K/M/B 规则不变，0 值过滤、降序、色表与 tooltip 分流规则不变。

**R10 外部数据只读。** 全程不写、不移动、不备份 `~/.workbuddy` 下任何文件；派生库可删可重建，重建成本是一次全量日志扫描。

## 验收标准

- **AC1 口径基线**：固定 fixture 手算 Σ步骤与请求级四项一致；本机全库 80.6M → 1,845.6M、DS 42.4M → 1,302.5M、459 步请求 653,057 → 176,950,725；单步请求新旧一致。基线随原始数据变化时按同口径重算，不得直接写死为断言常量。
- **AC2 约束**：C3 恒等式与 C4 缓存归属在逐步求和后成立；逐步事实的条数与该请求 `step_count` 一致；跨文件副本不重复计数；构造多模型 fixture 断言请求级模型等于第一步模型、全部 token 与积分都归到该模型、解析告警被记录，且不发生按步分摊。
- **AC3 比率数值**：固定 fixture 断言分子、分母、比率与手算一致；本机全区间 4.16× → 0.203×，10-26 / 27 / 28 / 31 约 0.117 / 0.115 / 0.133 / 0.113；按步判档与按请求判档的差异符合预期；分母 0 → `null`，分子 0 → 0，跨月按各自单价，无 DS 请求时 `ratios` 为空。
- **AC4 交叉验证**：`credit ÷ 逐步官方费用` 的隐含单价在闲时组与高峰组接近（约 0.04 元/积分），用固定 fixture 断言；现口径下的不自洽结果不得再出现。
- **AC5 结构兼容**：四个数据读取端点的字段、顺序、粒度与 `rows` / `ratios` 形状不变；积分聚合结果与明细结构不变；按模型分组、筛选、堆叠与分段的结果结构与旧版一致，只有数值变化。
- **AC6 前端**：token 数值放大后 K/M/B 格式正确；0 值过滤、降序、第二 Y 轴、单条折线、`null` 断线、不进图例、tooltip 分流、非 DS 筛选时折线隐藏且无新增文案；积分 tab 数值不变；既有旧口径说明文案已移除，界面无本次新增说明文字。
- **AC7 时间无关性**：同一组绝对时间戳在至少两种不同 `TZ` 环境下，`date_key`、每步闲时判定、比率序列与时间格式化结果一致；覆盖 UTC+8 零点与峰谷边界。
- **AC8 重建**：`schema_version = 5`，旧库启动后自动删库重建；重建前后请求数一致、外部 `workbuddy.db` 及 `-wal` / `-shm` 的大小与 mtime 不变。
- **AC9 回归**：既有筛选、tab、排序、色表、tooltip 0 值过滤、跨度上限、默认近 3 天、分组归一化、模型颜色绑定等验收项继续通过。
- **AC10 检查与文档**：`npm run typecheck`、`npm test`、`npm run build`、`npm run acceptance` 通过；`product-brief.md`、`technical-architecture.md`、`data-model.md`、`integration.md`、`deepseek-pricing.md`、`devops.md` 按实际实现同步，文档与代码无已知矛盾，旧交付文档未被改写。

## 待确认问题

无。以下四项已在需求确认阶段定案：

1. 以逐步用量事实为数据底座，请求级 token 与官方等效费用都由逐步求和派生，不以「只扩请求行聚合列」替代。
2. 闲时档位按每步自身时间戳判定，不复用请求级 `is_deepseek_offpeak`。
3. 分子保留「满额摊销」单价，正名为「摊销费用」；不改为按当月实际用量分摊，也不改用逐步 `rawUsage.credit`。
4. 一个请求视为单模型，取第一步的模型标识作为整个请求的模型；不处理多模型，不做按步分摊或主模型选举。
