# 模型固定基础色 Spec

## 背景与目标

趋势图当前按「不带筛选的全量模型集合」的**展示名排序序号**取色（`src/web/display.ts` 的 `modelColorIndex()`，`TrendChart` 再按 `PALETTE[色位 % 12]` 上色）。颜色因此取决于模型在集合中的位置，而不是模型本身：

- 新增或消失一个模型，排序后位于其后的模型色位整体平移，集体换色；
- 展示名规范化或重名后缀变化（`docs/data-model.md` C12）改变排序，同样换色；
- 全量模型集合请求 `/api/breakdown?dim=model` 返回前色位索引为空，图表先按当前可见集合顺序上色，返回后重排，**首屏有一次可见变色**；
- 模型超过 12 个时取模复用，两个模型同色；
- 颜色只出现在趋势图，按模型拆分、模型下拉、请求明细都没有对应色标，无法形成跨视图的长期识别。

目标：每个模型有一个由**业务键**决定的固定颜色，跨刷新、跨筛选、跨 tab、跨模型集合增减、跨展示名变化都不变；**名字同系列的模型共享一个基础色相、颜色相近**（如 hy3 / hy4 系列、kimi 系列），不同系列之间色相拉开；同一颜色在趋势图、按模型拆分、模型下拉、请求明细中一致呈现，且首帧即稳定。

统计口径、聚合结果、筛选行为、0 值隐藏、展示名规则全部不变；本交付是纯前端展示层改动。

## 与既有交付的关系

本 Spec 覆盖 `usage-panel-polish-spec.md` 已确认决策中「趋势图色位按不带筛选的全量模型拆分结果固定」这一条的实现方式，以及其 R8 里「不改着色与筛选行为」隐含的按集合排序取色。R7（0 值隐藏）、R3（列表截断）、R2（tab 状态）等其它规则保持不变。归档的 `docs/delivery/v1.0.0/` 与已完成的 `usage-panel-polish-*` 交付文档不改写。

长期文档需按本 Spec 更新：`technical-architecture.md`（面板层配色描述，删除额外全量模型查询的说明）、`docs/model-colors.md`（新增专题文档，记录色表、系列前缀表与分配规则）、`product-brief.md`（成功标准补充「模型颜色长期稳定」）。`data-model.md`、`integration.md`、`devops.md` 不涉及。

## 范围与非目标

**范围**

- 建立「模型业务键 → 固定颜色」的确定性映射：显式色表按系列分组（当前 11 个标识 + 「未知模型」），同系列共享基础色相、系列内用深浅档位区分成员；未见过的标识按静态前缀表归入系列或走稳定哈希兜底。
- 新增同系列模型自动落到该系列色系内；档位只由标识决定，不随其它模型增减变化。
- 色标贯穿趋势图系列与图例、按模型拆分行、模型下拉项、请求明细的模型列。
- 移除 `modelColorIndex()` 及仅为配色发起的 `/api/breakdown?dim=model` 全量查询。
- 纯函数单测、交互验收断言、长期文档同步。

**非目标**

- 不改统计口径、API 契约、数据库结构与 `schema_version`；颜色不入库、不落配置。
- 不改筛选、0 值隐藏、明细折叠、tab 状态、数值单位、展示名规范化与重名处理。
- 不提供用户自定义颜色、颜色配置界面、持久化或深浅主题切换（面板固定浅色）。
- 不套用厂商品牌色，不按模型语义推断系列（系列只按标识前缀的静态规则判定），不做随用量或时间变化的动态着色。
- 不引入新依赖，不改 `~/.workbuddy` 下任何原始数据。

## 用户或系统行为

1. 任一模型在趋势图、按模型拆分、模型下拉、请求明细中的颜色一致，颜色只由模型业务键决定。
2. 新增模型、刷新数据、切换时间 / 分组 / 对话 / 模型筛选、切换 tab、展示名变化，都不改变已有模型的颜色。
3. 首帧即稳定：颜色不依赖任何异步返回的模型集合，页面首次渲染时就是最终颜色。
4. 色表里没有的新模型标识自动获得一个稳定颜色；若其前缀命中已知系列，颜色落在该系列色系内、与同系列模型相近，否则按稳定哈希取色。
5. 同系列模型颜色相近但彼此可区分；不同系列之间颜色明显拉开。
6. 「未知模型」使用固定中性色，与所有正常模型的颜色区分。
7. 0 值隐藏、列表截断等既有展示规则不受影响：被隐藏的模型再次出现时颜色与隐藏前一致。

## 业务规则

**R1 绑定键**：颜色绑定模型业务键 `model`，即 `BreakdownRow.key`、`TimeseriesRow.model`、`RequestRow.model` 三者共用的标识；**不使用展示名**，避免 C12 的规范化与重名后缀影响颜色。

**R2 显式色表（按系列分组）**：每个系列占一个基础色相，系列内成员是该色相下的固定深浅档位；当前 11 个标识与「未知模型」共 12 项，色值清单记入 `docs/model-colors.md`。色表是只增不改的清单：以后新增标识不得重排或重新分配已有项。下表为待确认草案。

**R2b 系列归属**：系列由标识的静态前缀表判定，取最长匹配：`hy` → hunyuan、`kimi` → kimi、`deepseek` → deepseek、`glm` → glm、`mimo` → mimo、`minimax` → minimax、`step` → step。`hy` 用短前缀，使 `hy3`、`hy4` 及 `hy4-*` 变体同属一个系列；`minimax` 与 `mimo` 靠最长匹配区分。前缀表只增不改，不根据展示名、厂商或模型语义推断。

**R3 未知标识兜底**：不在色表的标识，先按 R2b 匹配系列：命中则在该系列基础色相下，用稳定哈希从**该系列未被显式占用的档位**中取一档；未命中则按稳定哈希从全局色板取色，与其它系列色相相近时用深浅档位拉开。哈希只读取标识字符串本身，结果与浏览器、时间、筛选、刷新次数、其它模型是否存在无关；同一标识多次计算必须得到同一颜色。「未被显式占用的档位」由静态色表定义，不随数据集合变化。显式色表内标识不参与哈希。

**R4 档位与撞色**：同系列成员本来就共享基础色相、靠深浅档位区分；档位值写入色表或由 R3 的哈希决定，都只由标识自身算出，不随其它模型增减而变化。不同系列若因哈希落到相近色相，用深浅档位拉开。若两个新标识恰好同色相且同档位，允许同色并在 `docs/model-colors.md` 记为已知限制。趋势图中同系列相邻堆叠块必须可分辨（实现方案在 Plan 中确定，例如细白色描边），但不改变色相与档位值。

**R5 色标呈现**：色标为小尺寸实心色点，颜色与趋势图对应系列的填充色逐值一致；色点不改变行高、不承载数值、不影响既有点击与筛选交互。明细表同一模型的多行色点一致。

**R6 口径不变与分层**：颜色计算全部在前端展示层，服务层聚合 SQL、五个 API 端点、数据库、刷新流程均不变。删除 `App` 中仅为配色发起的 `modelPalette` 查询；0 值隐藏的判定集合仍是 `modelOptions`，两者互不混用。

**R7 兼容**：模型是否在色表中、是否有用量、是否在当前 tab 可见，都不影响颜色计算；筛选下拉「当前值不在选项里」的兜底 option 同样按业务键取色。

## 边界情况

| 情况 | 处理 |
| --- | --- |
| 出现色表外的新模型标识 | 前缀命中已知系列则落在该系列色系内，否则稳定哈希取色；立即有颜色且长期不变，不需要改代码 |
| 出现同系列新模型（如 `hy5`、`kimi-k4`） | 自动使用同系列色相的不同档位，与已有同系列模型颜色相近 |
| 新标识与已有模型撞色 | 同色系深浅档位区分，基础色相不变 |
| 同系列多个模型同时出现在堆叠图 | 深浅档位配合边界描边保证相邻块可分辨，不改变色相 |
| 展示名规范化或追加 `(标识)` 后缀 | 颜色不变，因为绑定的是业务键 |
| 全量模型集合请求失败或尚未返回 | 不再有该请求；颜色首帧可用，无空窗期 |
| 模型在当前 tab 被 0 值隐藏 | 不显示该色标；再次出现时颜色不变 |
| 模型数量超过系列档位容量 | 档位复用 + 哈希变体区分，不报错、不截断 |
| `未知模型` | 固定中性灰，不参与哈希 |
| 明细表中同一模型多行 / 下拉兜底 option | 按同一业务键取色，保持一致 |
| 刷新后新增模型 | 已有模型颜色全部不变，仅新模型按系列规则得到一个相近色 |

## 验收标准

- **AC1 稳定性**：同一模型在 Token / 积分 tab、不同时间 / 分组 / 对话 / 模型筛选、刷新前后的颜色一致；单测覆盖「集合成员变化」「集合顺序变化」「展示名变化」三类输入下颜色不变。
- **AC2 确定性**：色表 12 项颜色互不重复且与 `docs/model-colors.md` 一致；单测断言同系列色相一致、系列内各档互不相同、不同系列可辨；未知标识重复计算结果一致；构造新标识用例时，命中系列前缀的必须落到该系列色相。
- **AC3 首帧稳定**：网络请求中不再出现仅为配色的 `/api/breakdown?dim=model`；首次渲染的系列颜色与稳定后一致，无中途变色。
- **AC4 跨视图一致**：趋势图系列与图例、按模型拆分行、模型下拉项、请求明细模型列的色点，对同一模型取到同一个色值；同系列相邻堆叠块边界可分辨。
- **AC5 口径回归**：五个 API 端点响应结构不变，0 值隐藏、列表截断、tab 状态、数值单位行为不变；v1.0.0 与 `usage-panel-polish` 的既有验收项继续通过；`npm run typecheck`、`npm test`、`npm run build` 通过，`npm run acceptance` 的颜色相关断言通过。
- **AC6 文档**：色表、系列前缀表与分配规则写入长期文档，代码与文档不存在已知矛盾；`docs/model-colors.md` 说明新增标识时如何扩表。

## 已确认决策

- 采用「已知模型手工指定颜色 + 新模型按标识稳定哈希兜底」，不采用纯哈希、不采用新模型统一灰。
- **基础色按系列分配**：标识前缀相同或相近的模型共享一个基础色相，系列内用深浅档位区分（用户要求名字相近的模型颜色也相近）；不同系列色相拉开。
- 色标覆盖趋势图 + 按模型拆分列表 + 模型下拉 + 请求明细，不只改趋势图。
- 撞色 / 档位冲突用同色系深浅变体，不扩大色板、不允许直接撞色。
- 颜色绑定业务键 `model`，不绑定展示名；颜色不入库、不进入 API。

## 待确认问题

1. R2 的 12 项色值与系列划分为草案，需确认：hunyuan 五档蓝色阶梯是否够分辨、deepseek 橙红与 step 暗金是否够拉开、未知模型是否保留灰。
2. 模型下拉目前是原生 `<select><option>`，多数浏览器不能可靠渲染彩色色点；需在 Plan 阶段确认呈现方式：自定义下拉列表（可显示色点、需处理键盘与 ARIA）、option 文本着色，或仅在下拉外显示当前选中模型的色点。该选择影响 R5 的验收细节与改动范围。
3. 系列内档位数、明暗幅度与堆叠块边界处理方式待 Plan 确认，原则是白底可读、同系列仍认得出、不同系列不混淆。
