# 产品简报

<!-- 记述产品与业务的稳定事实，作为需求判断和范围取舍的依据。不写实现细节和过程。 -->

## 背景

WorkBuddy 在本地记录每次对话的用量：会话内容与 token 用量写在 `~/.workbuddy/projects/<项目>/<会话>.jsonl`，积分与上下文占用写在 `~/.workbuddy/workbuddy.db`。这些数据面向运行而非面向使用者，没有跨会话的汇总视图。想知道"这段时间花了多少、花在哪些项目上"，只能逐个会话翻看，无法按时间、项目或模型横向比较。

## 目标用户

使用 WorkBuddy 的个人开发者，单机、单用户、数据不出本机。

## 核心问题

- 本周、本月在 WorkBuddy 上消耗了多少 token 和积分，趋势是升还是降。
- 消耗集中在哪些项目、哪些对话、哪些模型上，是否存在明显偏离的个例。
- 单个对话的成本构成如何：输入、输出、缓存命中各占多少。
- 缓存命中率是否随使用改善，高 token 的请求是否带来了相应产出。

## 业务目标

- 用一个本地面板回答上述问题，替代手工翻日志。
- 统计口径唯一且可解释：同一份原始数据，按文档口径重算应得到相同数字。
- 原始数据只读，不修改、不搬移 WorkBuddy 的任何文件。

## 范围

- 解析本地 WorkBuddy 数据：会话 jsonl（token、模型、时间、所属项目）与 `workbuddy.db`（积分、会话元信息）。
- 统计维度：日期、项目、对话（会话）、模型。
- 统计指标：输入 token、输出 token、缓存命中 token、合计 token、积分。
- 交付形态：本地 Web 面板，支持总览、按维度下钻、时间趋势。

## 非目标

- 不做多用户、账号体系、云端部署或数据上报。
- 不做实时监控与告警，数据按需增量刷新，不是流式。
- 不统计 WorkBuddy 之外的用量来源。
- 不按官方计价规则反推金额，积分直接取原始记录值。
- 不修改、清理、归档 WorkBuddy 原始数据。

## 关键术语

- **请求（request）**：一次用户输入触发的完整模型调用链，由 `conversationRequestId` 标识，内部包含多次工具调用步骤。积分的记录粒度就是请求。
- **步骤（step）**：请求内的一次模型调用，对应 jsonl 中一条带 `usage` 的记录。
- **累计用量**：同一请求内各步骤的 `usage` 是累计值而非增量，最后一步的数值代表该请求的总量。把各步骤相加会重复计算。
- **积分（credit）**：WorkBuddy 记录的消耗单位，存于 `session_usage.credit_json`，键为 `conversationRequestId`。
- **会话（session）**：一次连续对话，对应一个 jsonl 文件，同时对应 `sessions` 表中的一行。

## 成功标准

- 口径可复核：任取一个会话，面板显示的 token 与积分，等于该会话原始记录按本文档口径重算的结果。
- 打开即可看：增刷后不需要等待全量重算。
- 一次下钻到位：在同一界面内完成"某月 → 某项目 → 某模型 → 某对话"的逐层查看。
- 抗格式变化：WorkBuddy 升级导致日志字段变化时，只需改解析层，面板层不受影响。

## 待确认

- 积分是否存在有效期、赠送额度等需要在界面上单独呈现的语义。
- 是否需要导出（CSV 或图片）用于对外汇报。
- 是否需要按"上下文占用接近上限"给出提示（`session_usage` 记录了 `used` 与 `size`）。
