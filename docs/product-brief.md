# 产品简报

<!-- 记述产品与业务的稳定事实，作为需求判断和范围取舍的依据。不写实现细节和过程。 -->

## 背景

WorkBuddy 在本地记录每次对话的用量：会话内容与 token 用量写在 `~/.workbuddy/projects/<编码cwd>/<会话>.jsonl`，积分与上下文占用写在 `~/.workbuddy/workbuddy.db`。这些数据面向运行而非面向使用者，没有跨会话的汇总视图。想知道"这段时间花了多少、花在哪些分组上"，只能逐个会话翻看，无法按时间、分组或模型横向比较。

## 目标用户

使用 WorkBuddy 的个人开发者，单机、单用户、数据不出本机。

## 核心问题

- 本周、本月在 WorkBuddy 上消耗了多少 token 和积分，趋势是升还是降。
- 消耗集中在哪些分组、哪些对话、哪些模型上，是否存在明显偏离的个例。
- 单个对话的成本构成如何：输入、输出、缓存命中各占多少。
- 缓存命中占输入多少，单次请求的 token 消耗分布如何。

## 业务目标

- 用一个本地面板回答上述问题，替代手工翻日志。
- 统计口径唯一且可解释：同一份原始数据，按文档口径重算应得到相同数字。
- 原始数据只读，不修改、不搬移 WorkBuddy 的任何文件。

## 范围

- 解析本地 WorkBuddy 数据：会话 jsonl（token、模型、时间、所属分组）与 `workbuddy.db`（积分、会话元信息）。
- 统计维度：日期、分组、对话（会话）、模型。
- 统计指标：输入 token、输出 token、缓存命中 token、合计 token、积分、请求数、会话数。
- 交付形态：本地 Web 面板，**Token 与积分分成两个 tab**，共用时间、分组、对话、模型四个筛选条件；默认展示今天，时间粒度只有天，图表堆叠只按模型着色。每个 tab 各有一张请求明细表，默认折叠、按时间降序。

## 非目标

- 不做多用户、账号体系、云端部署或数据上报。
- 不做实时监控与告警，数据按需增量刷新，不是流式。
- 不统计 WorkBuddy 之外的用量来源。
- 不按官方计价规则反推金额，积分直接取原始记录值。
- 不修改、清理、归档 WorkBuddy 原始数据。
- **不追溯补齐本地已不可读的数据**：WorkBuddy 清理会话后消失的积分与日志、本地本就没有记账的子代理积分，都不补齐、不估算，只统计此刻能读到的部分。
- **不关注积分有效期、余额与赠送额度**，只统计消耗量。
- **不提供导出**（CSV、图片或分享链接）。
- **不做上下文容量提示**（`used` / `size` 不进入面板）。

## 关键术语

- **分组（group）**：按工作目录划分的统计维度，取值来自 `sessions.cwd`，与 WorkBuddy 桌面端新版的"分组"命名一致；旧称"项目"。不使用 `sessions.group_id` / `group_title`。
- **请求（request）**：一次用户输入触发的完整模型调用链，由 `conversationRequestId` 标识，内部包含多次工具调用步骤。积分的记录粒度就是请求。
- **步骤（step）**：请求内的一次模型调用，对应 jsonl 中一条带 `usage` 的记录。
- **累计用量**：同一请求内各步骤的 `usage` 是累计值而非增量，取 `total_tokens` 最大的那条代表该请求的总量；按时间排序的最后一条不一定是最大值那条。把各步骤相加会重复计算数十倍（本次实测约 40 倍，随请求步骤数变化）。
- **积分（credit）**：WorkBuddy 记录的消耗单位，存于 `session_usage.credit_json`，键为 `conversationRequestId`。积分为 0 与没有积分记录是两回事。
- **会话（session）**：一次连续对话，通常对应一个 jsonl 文件（续写时可能多个），同时对应 `sessions` 表中的一行；子代理会话归入父会话统计。

## 成功标准

- 口径可复核：任取一个会话，面板显示的 token 与积分，等于该会话原始记录按本文档口径重算的结果。
- 打开即可看：增刷后不需要等待全量重算。
- 首屏可读：总览、趋势与三个维度拆分能在一屏内看完，拆分列表不超过固定行数、不在列表内部滚动。
- 筛选即视图：时间、分组、对话、模型只有一份筛选，下拉框与拆分列表点击是同一动作的两个入口，结果完全一致；切换 tab 不重置筛选与明细状态。
- 抗格式变化：WorkBuddy 升级导致日志字段变化时，只需改解析层，面板层不受影响。
