# 子代理积分对账

## 背景

本地 `session_usage.credit_json` 的键只对得上主会话请求，子代理请求没有任何对应键，父会话也没有未匹配的孤键（实测快照见 `integration.md`）。当前口径把子代理请求按 `credit = 0` / `has_credit = 0` 计入，覆盖率分母包含子代理请求，界面标注「子代理无本地积分记录」；不补齐、不估算、不追溯是已确认的非目标。

## 问题

积分合计与覆盖率是否因「本地无记账」而系统性偏低，目前无法判断：缺的是数据本身，还是本地账的挂接方式。需要先拿一份外部积分明细与本地账逐请求对账，弄清子代理积分究竟怎么算，再决定处理方式。在结论出来之前，不改变现有统计口径。

## 预期价值

- 确认子代理请求是否单独计费、积分是否并入父会话的某条请求、或本来就不计费。
- 若对账发现本地确实漏挂，评估能否只补挂到派生库，使积分合计与覆盖率可解释。
- 若确认本地本就没有记账，把结论固化到 `integration.md`，避免后续重复排查。

## 已知约束

- 现有系统边界是只读 `~/.workbuddy` 下的本地数据，不联网、不读取云端官方用量接口（`technical-architecture.md` 系统边界）。引入「API 返回的积分明细」属于边界变更，需单独确认数据来源、鉴权方式与是否允许联网，不能直接在本项目里加请求。
- 口径已确认：不按 token 比例分摊、不估算、不追溯补齐；覆盖率分母包含子代理请求。任何调整都要先更新 Spec 与 `data-model.md` 的 C6，并重新验收维度一致性。
- 原始数据只读，派生库 `.data/index.db` 可删重建；即便补挂也只能写派生库，不写 `workbuddy.db`。
- 派生库已有 `requests.is_subagent` 与 `requests.session_id`（父会话），可支撑按父会话分组对账；对账键仍是 `conversationRequestId`。

## 待确认问题

1. 「API 返回的积分明细」具体指哪个数据源：WorkBuddy 云端用量接口、客户端本地缓存，还是其它导出文件？是否需要联网与鉴权？
2. 对账范围与判据：以哪个时间区间、哪些请求为样本，如何判定「子代理请求有积分」以及它挂在哪条记录上？
3. 若外部明细显示子代理有积分，是否允许把结果写入派生库？作为独立事实表还是补挂到 `requests.credit` / `has_credit`？刷新时如何保持幂等？
4. 若结论是本地确实不记账，是只更新文档结论，还是顺带调整覆盖率展示口径（例如把主会话覆盖率与全部请求覆盖率分开列）？
5. 对账是一次性排查，还是需要做成面板内可持续复核的视图？
