# 技术架构

<!-- 记述当前实现的系统结构与关键技术决策，不记录实现步骤和代码细节。 -->

## 系统边界

- **输入**：`~/.workbuddy/projects/**/*.jsonl`（会话事件流）与 `~/.workbuddy/workbuddy.db`（会话元信息与积分）。全部只读。字段与表结构见 [integration.md](./integration.md)。
- **输出**：本地浏览器面板；仓库内的派生索引 `.data/index.db`（可删除重建，不入库）。
- **不跨越的边界**：不向网络发送任何数据，不写 `~/.workbuddy` 下任何文件，不修改 WorkBuddy 配置。不追溯补齐本地已不可读的数据。**明确不接入云端官方计量接口**：2026-11-13 评估过 `POST /billing/meter/get-user-request-usage`，它只有请求级 `credit`、没有 `sessionId` / `groupId`（31 天内 58% 无法归属），四维统计不成立，接入成本与收益不匹配；对账改用仓库外的一次性脚本，证据见 [integration.md](./integration.md) 的「与官方账单的对比」。

## 模块划分

| 模块 | 位置 | 职责 |
| --- | --- | --- |
| 解析层 | `src/etl/` | 扫描 jsonl、按请求归并步骤、把外部业务键换成内部 `id`，产出请求级记录并维护派生维表 |
| 积分挂接 | `src/etl/` | 每次刷新无条件重读 `session_usage`，只更新当前映射中存在的请求，与文件增量解耦 |
| 索引层 | `.data/index.db` | 派生 sqlite：请求事实表 + 分组/会话/模型维表 + 扫描状态表，按文件 mtime/大小增量更新 |
| 服务层 | `server/` | 读索引做聚合查询，LEFT JOIN 维表补业务键与展示名，提供 HTTP API，生产模式下兼作静态资源服务器 |
| 面板层 | `src/web/` | React + ECharts，Token 与积分分两个 tab、共用一组筛选栏，不承担统计口径；模型配色按业务键静态映射，规则见 [model-colors.md](./model-colors.md) |

分层原则：**口径只存在于解析层与服务层**。面板层只渲染 API 返回值，不自行求和或换算，避免同一指标出现两套算法；唯一例外是缓存命中率，它由两个已返回字段求比，属纯展示派生，不参与任何聚合口径。两个 tab 是前端信息架构，后端端点共用，不为此拆分 API。0 值隐藏与拆分列表截断只影响展示，不改变任何聚合值。**面板查询不读 WorkBuddy 数据**，也**不接触派生库的内部 `id`**：API 一律用业务键字符串。模型配色同属纯展示派生：由面板按 `model` 业务键查静态色表或稳定哈希得到，不由 API 下发、不写入派生库，也不为配色额外请求模型集合；规则见 [model-colors.md](./model-colors.md)。

筛选栏的时间预设、分组、对话、模型四个下拉共用同一份 `Select` 组件（button + `role="listbox"`），选项完全由服务层聚合结果驱动，面板不推断分组归属；日期区间仍是原生 `input[type="date"]`。趋势图 tooltip 只列出当天数值大于 0 的模型并按数值降序，全 0 时显示日期与「无数据」；这只是提示内容的过滤，`series.data` 仍按天补 0，堆叠、坐标轴与合计口径不变。

## 关键依赖

| 依赖 | 用途 | 说明 |
| --- | --- | --- |
| Node.js ≥ 24 | 运行时 | `node:sqlite` 零依赖、免 native 编译；本机 24.19.0（`E:\Software\nodejs`）实测可用且无实验性警告，选择理由见技术约束 |
| TypeScript + `@types/node` | 全仓类型 | 解析结果类型即 API 契约，贯穿到面板 props；`node:sqlite` 类型由 `@types/node` 提供 |
| Vite + React | 面板 | 开发期热更新 |
| ECharts | 图表 | 按天趋势与按模型着色的堆叠 |
| Hono + `@hono/node-server` | 服务层 | 端点数量固定、按维度拆分查询，路由与中间件比手写 http 清晰；生产模式由 Node 适配器提供静态资源 |

不引入 ORM 与状态管理库：派生库只有五张表（事实表、三张维表、扫描状态表）与一张单行配置表，数据量在千行量级（实测快照见 [integration.md](./integration.md)）。

## 数据流

```
~/.workbuddy/projects/**/*.jsonl ──→ 文件增量解析 ────┐
~/.workbuddy/workbuddy.db ─┬─→ 积分挂接（每次刷新）──┼─→ .data/index.db ─→ 服务层聚合 ─→ HTTP API ─→ React 面板
                           └─→ 元信息同步（维表）────┘
```

一次刷新包含互不依赖的几步：按 `source_files` 的 size/mtime 找出变化的 jsonl 并整文件重解析，以来源文件 `id` 为单位原子替换该文件贡献的请求行；从 `sessions` 表同步会话与分组维表；从 `session_usage` 合成 `requestId → 积分` 映射，只更新映射中存在的请求，映射外的行不触碰、不主动清零。

文件没有变化也要重读积分（补上晚到的记录），积分表没有变化也不影响文件解析。刷新时机：`npm start` 启动时执行一次，面板的手动刷新触发同一流程，由进程内互斥锁防止并发重复执行。不做文件监听，避免与 WorkBuddy 运行时的频繁写入互相干扰。

## 接口

服务层不暴露原始日志，除刷新入口外均为只读端点。参数与返回值一律用**业务键字符串**：时间 = `from` / `to`（`YYYY-MM-DD`）、分组 = `group`（`cwd`；自动目录不按具体路径传参，统一用虚拟键「默认」）、对话 = `session`（WorkBuddy 会话 ID）、模型 = `model`（模型标识）；不提供其它筛选开关。服务层 LEFT JOIN 维表后直接用业务键列过滤（筛选时不转换成内部 `id`），同一 JOIN 取得展示名；维度筛选值从 JOIN 结果的业务键 `DISTINCT` 取。内部 `id` 不出现在 API 中，删库重建后它们会重新分配。

| 端点 | 返回 |
| --- | --- |
| `GET /api/summary` | 区间合计：token 四项、积分、请求数、会话数；顶层另返回上次刷新完成时间 `lastRefreshAt`（与筛选无关，从未刷新为 `null`） |
| `GET /api/timeseries` | 按天、按模型拆分的序列，支撑按模型着色的堆叠；粒度固定按天 |
| `GET /api/breakdown?dim=group\|model\|session` | 按单一维度拆分的聚合与占比 |
| `GET /api/requests` | 请求级明细，用于表格与排序 |
| `POST /api/refresh` | 触发一次刷新，返回扫描文件数、新增或更新请求数、补挂积分条数、耗时 |

所有返回值为聚合结果或请求级明细，不下发原始 jsonl 内容。

**分组口径归一化**：WorkBuddy 按时间戳自动创建的工作目录形如 `<...>/WorkBuddy/yyyy-MM-dd-HH-mm-ss`。判定在解析层写入 `groups.is_auto` 时按路径形态完成（`/` 与 `\` 都接受，父段 `workbuddy` 大小写不敏感，不校验日期合法性），服务层据此把全部自动目录聚合为一行「默认」，`group=默认` 映射为 `is_auto = 1`。**判定只有解析层一处**，服务层与面板都不重复路径规则。展示名恰为「默认」的手动分组不做回退，其业务键仍是完整路径，因此下拉可能出现两个同名项、筛选互不影响。API 结构不变：`/api/requests` 的 `group` 仍是原始 `cwd`，只有 `groupName` 归一为「默认」；自动目录判定规则变化时必须递增 `schema_version` 重建索引（见 [data-model.md](./data-model.md)）。

## 部署方式

- 开发：`npm run dev`，Vite 起面板，API 单独起并通过 Vite proxy 转发 `/api/`（只匹配该前缀，避免误拦前端模块 `api.ts`）。
- 使用：`npm run build && npm start`，由服务层同端口提供静态资源与 API，浏览器打开 `http://127.0.0.1:<PORT>`（与 `HOST` 默认值一致；`localhost` 可能解析到 ::1）。
- 无容器、无反向代理、无进程守护需求，单机单进程即可。

## 技术约束

- **Node 版本**：PATH 首位是 WorkBuddy 托管的 22.22.2，本机另有 24.19.0（`E:\Software\nodejs`）。实测两者都能直接加载 `node:sqlite` 且 `readOnly` 生效，**均不需要** `--experimental-sqlite`（该 flag 自 22.13.0 / 23.4.0 起已取消）；差别是 22 会打印 `ExperimentalWarning`，24 不会。项目仍以 `engines` 声明 `>=24` 并在入口校验版本，理由是 24 为 LTS、无实验性警告、类型定义更完整，不依赖调用方 shell 的 PATH 顺序。
- **`node:sqlite` 稳定性**：该模块至今标记为实验性／发布候选（Stability 1.x），且自 25.7.0 起 `DatabaseSync` 已成为 `Database` 的弃用别名。`>=24` 不等于对未来主版本兼容；升级 Node 主版本前需回归解析与查询。
- **外部库只读**：`workbuddy.db` 为 WAL 模式，以 `readOnly: true` 打开，避免与运行中的 WorkBuddy 争锁。WAL 只读连接依赖同目录的 `-wal` / `-shm`，WorkBuddy 运行时二者存在；实测写入被拒，且 `workbuddy.db`、`-wal`、`-shm` 三个文件的大小与 mtime 在只读查询前后均未变化。
- **数据可得性**：只统计本地此刻能读到的数据。WorkBuddy 清理会话后其 `session_usage` 行会整行消失、部分 jsonl 也不再存在，由此产生的积分缺失不追溯、不补齐。子代理请求在本地没有独立积分键：团队子代理的积分并入父请求，普通子代理与 `custom_agent` 不记账（后者属真实缺口）；`has_credit` 只能表示本地账本有无键，无法区分免费模型、子代理与真缺失。`sessions.deleted_at` 不参与过滤。
- **数据量**：2026-11-13 实测 jsonl 140 个、约 187MB，归并后 434 个请求；维度规模为 11 个模型、66 个有请求的分组、105 个有请求的会话，LEFT JOIN 成本可忽略（数值随 WorkBuddy 清理而下降，快照见 [integration.md](./integration.md)）。分组口径归一化后自动目录在服务层合并为一行「默认」，分组行数不再随自动目录数量增长。`projects` 目录还含大量无关的 `.ndjson` 与 `.txt`，扫描按扩展名过滤。全量解析在秒级，因此增量更新仍是硬要求，不是优化项。
- **路径处理**：Windows 盘符与分隔符差异统一交给 `node:path`，不手拼字符串。**唯一例外**是分组自动目录判定：`cwd` 可能来自另一平台（备份、迁移），而 `node:path` 的分隔符随运行平台变化，因此该判定固定按 `/` 与 `\` 切分，与展示名取末段的写法一致。
- **日志格式不稳定**：WorkBuddy 升级可能改字段，解析层需集中字段映射并保留兼容分支。内部字段由本项目命名，外部键名由 WorkBuddy 决定，只能适配。

## 架构决策

**AD-1 全 TypeScript 单仓。** 面板是唯一交付物，类型从解析层一路贯到图表 props，改字段时编译器能兜住；代价是接受 node_modules 与构建步骤。Python 方案在解析上更省事，但把成本转移到了前端手写图表与跨语言契约上。

**AD-2 以请求（`conversationRequestId`）为核算单位。** 积分本身就是请求粒度，token 在该粒度内为累计值、取 `total_tokens` 最大那条即得请求总量，两者天然对齐；若按步骤统计，token 会重复计算数十倍（实测约 40 倍，随请求步骤数变化）。

**AD-3 派生索引用 sqlite 而非单个 JSON 文件。** 需要按文件原子替换、按维度聚合、按时间排序，sqlite 一条 SQL 就能覆盖；`node:sqlite` 零依赖，避免了 `better-sqlite3` 在 Windows 上的编译问题，代价是依赖实验性 API（见技术约束）。索引可删可重建，因此不承担数据安全责任。

**AD-4 聚合放在服务层。** 若把请求级明细全量下发到前端再聚合，数据增长后首屏会越来越慢；服务端返回小结果集，需要明细时再展开按需取。展示名与业务键由服务层 JOIN 派生维表取得，面板不接触外部数据。缓存命中率是唯一的前端求值项，只用于「缓存命中」指标卡的展示。

**AD-5 外部数据只读且不做备份。** 原始数据的所有权属于 WorkBuddy，本项目不复制、不归档，只派生。这样无论 WorkBuddy 如何清理旧日志，本项目都不会产生"过期副本"这类需要维护的东西。

**AD-6 日期归属取请求内最早步骤的本地时间。** 跨零点的长请求归入发起当天，符合"这天花了多少"的直觉；用本地时区而非 UTC，避免出现"晚上八点算到明天"的错位。派生出的 `date_key` 落库，把时区口径固化在解析层一次。

**AD-7 积分挂接与文件增量解耦。** `credit_json` 的写入时机与 jsonl 不同步，把积分挂接绑在"文件变化"上会让晚到的积分永久补不上。因此每次刷新都独立重读 `session_usage`，只按当前映射更新存在的请求；映射外的行不触碰。不做历史补齐，也不因外部记录消失而主动清零已读到的值。

**AD-8 事实表 + 派生维表，用内部代理主键关联。** 实测 903 个请求只对应 11 个模型、58 个有请求的分组、203 个有请求的会话，把会话标题和模型展示名重复存在每个请求里没有收益；集中在维表后，服务层一条 LEFT JOIN 即可取到。主键不用外部标识：`cwd` / `sessionId` / `model` 标识由 WorkBuddy 决定，可能变化、为空或重复（自定义模型与原生模型可能同名），用它们做主键会把派生库绑死在外部值上；改用自增 `id` 后，业务键只作为带 UNIQUE 约束的列，解析层按业务键换 `id`。代价是查询要 JOIN、重建后 `id` 会变，因此 API 一律用业务键，内部 `id` 不外露。当前原始日志没有可区分自定义模型来源的字段，同名自定义模型暂与原生模型合并为一行，属已知限制；若 WorkBuddy 后续提供该字段，再扩展维表。
